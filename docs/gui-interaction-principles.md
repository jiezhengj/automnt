
# 这份文档的用途

2026-10-22 的 GUI 设计反复表明：问题通常不在某个按钮的位置，而在层级、所有权和反馈归属没有先定。下面是从那轮反复修改中提炼出的稳定原则，适用于后续所有 GUI Feature，不必每次重新讨论。具体布局可以随 Feature 演进，这些原则不随单个界面漂移。

新 GUI Feature 开工前先读本文；`AGENTS.md` 的“GUI 交互原则”是最小集，本文是完整说明与检查清单。

# 产品核心必须在界面中心

- 自动挂载的开与关是产品核心：总开关、服务器开关、共享开关应当直接可见、可操作，占据主要视觉重量。
- “在 Finder 中打开”、诊断、手动挂载、索引设置是异常兜底或辅助动作，不能反客为主，不能成为共享行的第一主操作或界面主视觉。
- 判断一个控件该不该显眼，先问：它是在完成产品的核心承诺，还是在补救核心承诺失败？后者应退到展开区、设置或诊断入口。

# 动作按对象层级归属

界面按“全局 → 服务器 → 共享”三层组织，动作放在它所属对象的层级，同一动作只出现一次。

- 全局：添加共享、应用设置、服务器排序属于全局层。宽窗放在侧栏头部（标题旁的系统符号按钮），窄窗放在根层工具栏；不放在侧栏底部动作栏，不放在窗口工具栏冒充全局。
- 服务器：服务器参与自动挂载、服务器连接与索引设置属于服务器页。设置入口用工具栏符号 + 原生 sheet，不用文字胶囊或行内文字链。
- 共享：共享的自动挂载开关、状态、展开后的位置/手动操作/移除属于共享行。行内不重复全局或服务器动作。
- 不要因为“这里空着”就塞入口；空位不是放动作的理由。侧栏底部尤其不能变成全局动作的杂物抽屉。

# 反馈跟随动作发生地

- 用户在哪里发起动作，结果就在哪里出现；失败、冲突和确认都属于那个表面。
- 成功不弹 toast、不写“已保存”横幅：对象状态变化、开关位置变化、列表变化本身就是反馈。
- 失败必须留在动作所属的表面：排序失败在侧栏提示，设置保存失败在设置窗口提示，菜单栏动作的结果只在菜单栏显示，不把成功文案塞到右侧详情或另一个 pane。
- 不伪造状态。后台未运行、权限未授予、挂载未完成时显示真实状态和下一步，不用“已开启”的意图冒充运行成功。
- 冲突时保留用户草稿并给出明确的重读/放弃选择，不静默覆盖，也不把内部术语（revision、配置冲突、重新读取）直接丢给用户。

# 原位展开优先于下钻

- 查看对象详情优先在原位展开，不新增第二层页面、第二层 sheet 或导航栈。展开/收起由行本身控制，状态保留在窗口层。
- 只有“编辑”这类表单才使用一层 sheet；sheet 里不重复页面上已有的开关或状态。
- 展开区内部也要分组：位置 → 手动操作 → 分隔线 → 管理动作。操作动作与管理动作（编辑、移除）不要混在一行。
- 同一信息不要同时出现在行内和展开区：开关留在行内，状态留在行内，位置和低频动作才进展开区。

# 每个对象每个状态只有一个主操作

- 按当前状态只呈现一个主操作：未挂载时是连接/挂载，已挂载时是打开位置，异常时是修复。其余动作降为次要样式或收进展开区。
- 破坏性动作（移除、删除）用红色并与普通操作分开；需要真实后果时用确认对话框，不为例行操作增加确认。
- 低频动作不与主操作争夺视觉重量；不要用一排图标代替有文字的明确动作。
- 图标按钮不是“省地方”的借口：必须有可访问名称、悬停提示和明确语义；能用系统符号就不用自绘图形。

# 依赖链必须可见

- 总开关关闭 → 服务器开关禁用；服务器关闭 → 共享开关禁用。禁用之外还要有一行说明“为什么不可用、下一步做什么”。
- 开关表达用户意图，行内状态表达事实；两者不要混写。开关关闭不代表已挂载卷被弹出，文案必须说清已挂载卷仍可用。
- 服务器页先给服务器级开关，再给共享级开关；不要让用户去设置 sheet 里找总开关的入口。

# 先定状态矩阵，再画布局

- 画界面前列出所有状态：空、加载、失败、冲突、禁用、混合（部分共享可用）、多服务器、长名称/长路径、长译文、浅色、深色、较大文字、窄窗、宽窗。
- 列出状态之间的转移：启动、切换选中、展开/收起、推送/返回、总开关切换、服务器开关切换、挂载/弹出进行中与完成。
- 依赖状态和“进行中”状态必须在布局阶段就有位置；不要等实现后才发现没地方放进度或错误。
- 尺寸自适应：自然换行、自适应重排、必要时滚动；不靠缩小字号或固定宽高硬塞。

# 用系统原生组件，不发明装饰

- 优先 SwiftUI 原生导航、列表、表单、工具栏、设置窗口、菜单、sheet、alert、文件选择器与 SF Symbols。
- 玻璃只用于系统提供的 button style / 材质，不给容器随手加玻璃；不手绘窗口装饰，不伪造 macOS 控件。
- 全局符号按钮用系统 `.buttonStyle(.glass)` 一类原生样式；不要自造底栏、胶囊文字按钮或网页式悬浮按钮。
- 导航形态跟着宽度走：宽窗左右结构，窄窗用原生服务器 → 共享 → 详情导航，返回后保留选中、焦点和滚动。
- 搜索、工具栏、空状态使用系统标准放置；不把搜索框塞进页面中部，不为每个页面发明一套局部导航。

# 真实窗口验收高于预览和测试

- 设计是否成立，以真实 macOS 窗口为准；预览、HTML、截图草图只能辅助构图，不能证明原生合规。
- 每个 GUI Feature 至少在宽窗（约 1100×700）和窄窗（约 620×700）检查：启动、实时拖动跨过宽度阈值、窄窗推送与返回、sheet、设置窗口、深浅色、长译文和较大文字。
- 实时缩放会暴露只在“启动即窄窗”时看不到的布局问题；两种路径都要测，不能只测一种。
- 失败、禁用、空、加载等状态要在真实窗口里触发或至少核对路径；只跑单元测试不算界面验收。
- 未验证项（VoiceOver、浅色、原生审校、真实后台状态等）如实写进证据，不用推断代替结论。

# 结构性反馈反复出现时，停止打补丁

- 同一个界面被反复指出同类问题时，不要继续逐点挪控件；先汇总全部反馈，判断根因是不是层级、所有权或反馈归属错了。
- 从零写一份交互架构：逐条把反馈映射到结构决定，再一次性实施；不要一个问题打一个补丁，否则会来回震荡。
- 已确认的原则不因单个截图或单次不满而推翻；要做的是把原则应用到全界面，而不是只修被举例的那一处。
- 记录被否决的方案和理由，后续不再重复提出；设计文档要能解释“为什么不是另一个布局”。

# 原则与布局选择分层

- 稳定原则：核心功能优先、动作归属层级、反馈跟随发生地、原位展开优先、依赖链可见、原生组件优先。后续 Feature 直接继承，不需要重新论证。
- 可变布局：具体的侧栏头部样式、展开区顺序、工具栏符号、间距与动效，可以随平台版本和新 Feature 调整；调整时不得违反上面的稳定原则。
- 不要把某一版的像素布局当成永久规则；也不要以“新 Feature 不一样”为由绕开原则。
- 已实施案例见 `specs/005-swiftui-mas-gui/design/interaction-architecture.md`；它只作为原则如何落地的例子，不作为后续 Feature 的布局模板。

# 文案与无障碍不是收尾工作

- 标签从用户动作和结果出发，简短明确；后果与限制放在控件旁边的辅助说明里，不用括号把相反动作塞进一个标签。
- 名称、状态、解释分别表达：开关叫“自动挂载”，说明解释关闭后的影响；不要把解释写成开关名称。
- 图标按钮、开关、展开行都要有包含对象名称的可访问标签；键盘要有等价操作。
- 九种语言从设计阶段就考虑长译文与语序变化，不靠截断或缩小字号；机器翻译不能替代原生审校，未审校内容明确标注。
- 破坏性后果、权限失败、冲突恢复要给出可执行的下一步，不复述错误码，不暴露实现概念。

# 新 GUI Feature 的检查清单

1. 写出状态矩阵：正常、空、加载、失败、冲突、禁用、混合、多对象、长文本、窄/宽窗、深浅色、较大文字。
2. 画所有权表：每个动作属于全局、服务器还是共享？是否只出现一次？是否放在了正确的表面？
3. 画反馈表：每个动作失败/成功分别显示在哪？成功是否真的需要提示？是否会把成功文案放到别的 pane？
4. 决定展开还是导航：能否原位展开？是否多了一层页面/弹窗？编辑是否只有一层 sheet？
5. 检查依赖链：总开关、服务器、共享的禁用与说明是否齐全？开关表达意图、行表达事实是否分开？
6. 原生控件审计：是否用了系统组件？玻璃是否只来自系统样式？图标按钮是否有可访问名称？
7. 真实窗口验收：宽窗、窄窗、启动、实时缩放、推送/返回、sheet、设置窗口、深浅色、长译文；记录未验证项。
8. 更新文档与证据：交互架构、任务、截图索引；把新出现的稳定原则补进本文，而不是只留在本次 Feature 的文档里。

# 明确避免的反模式

- 把“在 Finder 中打开”当成核心功能，把自动挂载开关藏起来。
- 侧栏底部放一排全局动作按钮，或窗口工具栏里塞全局添加/设置。
- 同一界面出现两个设置图标，或服务器设置用一个不显眼的文字按钮。
- 在服务器设置 sheet 里重复页面上已有的自动挂载开关。
- 排序成功后在右侧详情写“顺序已保存”，或任何成功 toast。
- 为共享详情再开一层页面/弹窗，或让展开区重复行内开关和状态。
- 图标动作没有文字、没有提示、没有可访问名称。
- 文案塞在“看起来空着”的地方，而不是动作发生的表面。
- 只在启动时窄窗检查，不测实时缩放跨阈值。
- 用预览/HTML 截图宣称原生合规，或用单元测试代替真实窗口验收。
- 反复打补丁而不重新审视层级和所有权。
