**发现并修正的真实缺陷（构建脚本层）**：`scripts/build.sh` 原先不执行任何签名，而 CLI 的 `--install`/`BinarySigningPolicy` 要求候选具备 `anchor apple generic and identifier "automnt"` 的有效签名——因此该脚本的默认输出**无法自我安装/替换**（实测报“代码签名无效或与已安装版本身份不兼容”）。同时确认签名 identifier 必须恰为 `automnt`（用 `org.automnt.cli` 或省略都会被拒）。**已修复**：脚本现在显式签名并 `--strict` 验证，身份优先复用现有根二进制已用的证书（因为 Designated Requirement 内嵌叶子证书 CN，换证书会改变系统识别到的程序身份，与宪法 V 冲突），否则回退到本机任一 Apple Development/Developer ID Application；找不到身份时明确告警而不静默产出无法安装的二进制。可用 `AUTOMNT_SIGN_IDENTITY` 显式指定。修复后实测：脚本产物 `signed: … (identifier automnt)`、strict 通过、`--install` 真实注册成功；并且新产物满足被替换方（根二进制）的 Designated Requirement，**身份连续性保持**。

**发现并修复的真实缺陷（全新安装永远失败）**：`CLIOwnership.registrationRefusal()` 在**无配置文件**的首次安装时，让 `FileConfigRepository.read()` 的 ENOENT 落入通用 `catch`，返回 `requiresRepair`；而 `--install` 在调用 `performRegistration()` 之前先做该预检，于是**全新机器上的首次安装必然被拒**（日志 `CLI registration precheck failed: … Code=2 "No such file or directory"`）。`performRegistration()` 本身已正确处理“无配置不建立与文件不符的所有权状态”分支，只是永远轮不到执行。修复：在预检中把 ENOENT 与真正的读取失败分开，前者放行给 `performRegistration()`。修复后在同一台真实干净系统上 `--install` 成功注册 `com.user.automnt`（此前每次必失败）。`swift test` 285 项仍全绿。

**发现但未修复的真实缺陷（CLI 无中断转换恢复入口）**：真实测试中我用 `launchctl kickstart -k` 在服务转换进行中重启了守护进程，使持久状态停在 `owner=cli / phase=stopping`（journal 的 `pending` 未完成）。此后 CLI 的所有入口（`--install`、`--config`、直接运行评估）都只返回 `requiresRepair`/`transitionInFlight`，**没有任何 CLI 修复入口**：`HandoffCoordinator.recoverInterruptedTransition` 只有 GUI 调用，而 GUI 的调用点又显式要求 `owner != .cli`，因此 CLI 拥有的楔住状态在两端都无法恢复。最终用 `--uninstall --purge` 清理后重建才恢复。这是真实的健壮性缺口（触发条件是我人为中断转换，但同类中断在崩溃/强杀时也可能出现），应补一个 CLI 侧的显式恢复入口。

## 需要维护者决定的取舍：GUI 如何看到 CLI 配置

现象：沙盒 GUI 打不开 `~/Library/Application Support/automnt`，于是显示“没有任何已管理服务器”，而 CLI 里明明配好了两台。可选做法及其用户可见变化与风险：

| 方案 | 用户看到什么 | 风险/代价 |
| --- | --- | --- |
| A. 一次性授权配置文件夹 | 首次打开弹一次“允许 Automnt 访问其配置文件夹”，之后自动同步 | 需要一次文件夹授权对话框，接近此前被撤销的“选择内部目录”，但是一次性的、目录已固定，不是让用户挑位置 |
| B. CLI 也改用 App Group 容器 | 两入口天然共享配置，无任何授权提示 | App Group 路径含 Team ID，开源用户自行编译/自签时会落到不同路径，**破坏 CLI 的可移植性与既有用户配置位置**，且需迁移 |
| C. GUI 不走沙盒 | 直接读写规范目录，无提示 | 很可能不符合 Mac App Store 沙盒要求，与商店渠道目标冲突 |
| D. GUI 用特权 helper 代读配置 | 无提示即可看到 CLI 配置 | helper 需承担配置读写所有权，复杂度与安全面显著上升，仍需与 CLI 协调单 owner |

现状相当于 A 被撤销后没有任何替代方案，因而承诺落空；建议先定方向再继续实施。

# 2026-10-21 维护者复核后的第一轮修订

维护者指出：同一界面存在两个“设置”图标、图标按钮没有提示文案、点闪电后出现无法处置的“配置已在另一个窗口或命令行中更改”，并要求彻查全部交互与文案。三份只读审计（入口清单、死路与黑箱、九语文案）确认问题不是个别按钮，而是入口命名、结果反馈与技术语言三类结构性缺陷；本轮先修其中会直接影响“能不能用、会不会迷路”的部分。

## 已收敛的入口

- 应用设置只有一个入口：应用菜单“设置…”（⌘,）。删除侧栏底部齿轮；状态卡里的“设置”仍打开全局设置，但不再与对象级入口并列。
- 服务器级入口改名为“服务器连接…”，在详情工具栏带文字显示；它改的是这台服务器的连接参数，不再冒充“设置”。
- 全局动作带文字：底栏“＋ 添加共享文件夹…”“⚡ 立即检查”，并给“立即检查”补悬停说明“立即检查所有共享文件夹，把缺少的挂载起来”。

## 结果反馈的位置

动作结果不再只写进被遮挡的全局卡片：服务器详情把状态卡与动作结果纵向叠加（状态卡不再压制 `issue`/`notice`）；无选中、首次启动、权限页与窄窗根页有独立结果条；共享详情 sheet 顶部显示本次动作结果。动作从哪个表面发起，结果就出现在哪个表面。

## 冲突恢复

非表单动作遇到设置更新时不再让用户“重新读取”：模型自动采用最新设置并重试一次，仍失败才提示；只有表单保留“使用最新设置”按钮，且输入不丢。界面不再出现“另一个窗口或命令行”“你的输入会保留”这类与当前场景不符的句子。

## 本轮未覆盖

共享详情开关失败提示、服务器设置“完成”的保存模型、菜单栏动作结果与“添加共享文件夹…”的空动作、权限页“稍后”出口、移除最后一个共享的后果说明、窄窗推送后的添加入口、搜索无结果提示，以及全部九语的母语审校与深色/较大文字/VoiceOver 复验。上述项保留在 T120 的未完成清单与 `release/evidence/t112-t118-2026-10-21.md` 中。

## 2026-10-21 第三轮：按动线重做动作层级

上一轮把全局动作塞进侧栏底部并加文字，维护者否决：容器只有 220–260pt，任何长标签都会截断或挤压；全局设置退到系统菜单又发现不了。结论是这不是位置微调问题，而是作用域分层错误。

## 重新分层

- 窗口工具栏：只放全局/窗口级入口。添加共享文件夹用 ＋（macOS 通用符号，提供悬停说明与 ⌘N）；立即检查用文字按钮（闪电没有共识）；设置用齿轮＋“设置”，常驻 trailing，全窗口唯一。
- 侧栏：只做导航与排序，彻底移除底部动作条。
- 详情内容：对象级动作（服务器连接…、刷新状态）作为“服务器”分组的可见行，不再占用工具栏，也不再用滑杆等“设置类”图标。
- 状态与结果：后台状态卡继续在详情顶部说明实际运行状态；本轮不把立即检查并入状态卡，因为它是全局兜底动作，工具栏的常驻文字按钮更容易被发现。

## 依据与取舍

- 符号与文字：只有全系统有共识的符号（＋、齿轮、搜索、chevron）允许单独出现；其余动作必须带文字，且放在宽度足够的容器里（工具栏、内容行），不放在窄侧栏。
- 作用域隔离：全局动作在工具栏，对象动作在内容区，设置只有一处；避免“两个设置”和“这个按钮作用于谁”的歧义。
- 已知代价：窄窗（<700pt）工具栏放不下全部动作时，系统会把部分项收进溢出菜单；这是 macOS 原生行为，暂不自定义规避。

## 2026-10-21 第四轮：一个共享，一个动作

维护者指出：服务器设置找不到、页面按钮成堆、两个“在 Finder 打开”看不懂、刷新/检查多余、侧栏顺序说明很长。根因是把数据模型的字段逐个画成了控件。

## 页面原则

- 一个共享只有一个主动作，标签随状态变化：可用 →“在 Finder 中打开”；未挂载 →“连接并打开”；需登录 →“在 Finder 中连接”。主按钮永远打开真正可用的目录，不再区分“配置位置/实际位置”。
- 次要动作最多两个（如“弹出”），其余进入右上“⋯”：编辑地址与位置、使用当前位置、诊断、从 Automnt 移除。
- 服务器设置命名为“服务器设置…”，放在该服务器页工具栏，不再叫“服务器连接…”，也不放在页面底部。
- 状态先图形后文字：共享行用彩色状态符号（绿勾/灰圈/橙色三角）+ 简短状态，不用“挂载在其他位置”这类内部描述当告警。
- 刷新与检查不是界面按钮：界面靠激活与系统挂载通知自动更新；手动检查只放在“服务器”菜单（⌘R）和菜单栏额外项。
- 顺序说明图形化：行首序号 + 一行“已管理 · 按顺序”，长解释只在 ⓘ 提示里。

## 2026-10-21 第五轮：一个入口，一种按钮语义

- 窗口工具栏只放图标按钮：＋（添加）、齿轮（应用设置）、搜索框。工具栏不再有文字按钮，避免胶囊内文字被挤窄。
- 应用设置与服务器设置不再并列：全局设置永远是齿轮；服务器设置是服务器页顶部的一行“服务器设置 ›”（整行可点，文字完整）。服务器页不再有第二个设置按钮。
- “⋯”不用于承载对象动作：共享详情的低频动作改为通用图标（铅笔=编辑，垃圾桶=移除），主按钮保持唯一。
- 不提供临时性的界面按钮：顺序调整拖动即保存，不再出现“撤销顺序调整”；如将来需要撤销，应放进“编辑”菜单与快捷键，而不是列表里的临时行。
- 服务器自身属性（是否参与自动挂载、名称、地址、端口、索引）全部收在该服务器的“服务器设置”里，主页面只展示身份与共享列表。

## 2026-10-21 第六轮：不留假控件

- 解释性信息不得只挂在 hover 提示或无法点击的图标上；要么是可见的一行说明，要么是真实可点的控件。
- macOS 列表的分组标题不保证接收点击，因此不要把“了解更多”做成标题里的图标；说明直接用一行文字放在分组内。
- 窄窗列表里，说明文字作为分组脚注显示，不占列表行，避免把首行往下顶出空白。

## 2026-10-21 第七轮：按对象层级分配动作与容器

- 侧栏是服务器层级，负责全局动作：添加共享文件夹与打开应用设置放在侧栏底部动作栏；窗口工具栏不再放它们。
- 右侧是单台服务器的详情：服务器身份与“服务器设置”放在这里，用普通带内边距的按钮，不用工具栏文字胶囊、也不用文字链。
- 共享对象在主界面原位展开：状态、主操作、自动挂载开关、位置与低频图标动作都在行下展开；不再为查看详情开一层弹窗，编辑只保留一层 sheet。
- 展开状态由窗口持有，菜单栏“查看详情”与窄窗导航复用同一展开状态，不再有第二套详情界面。
- 列表根视图的底部动作栏用 VStack 放在列表下方，避免该样式下 safeAreaInset 在列表顶部产生空白。

## 2026-10-21 第八轮：从零重定架构，按层级与反馈归属实现

- 先写 `design/interaction-architecture.md`，把反馈逐条映射为结构性决定，停止在旧界面上逐点挪动控件。
- 层级与所有权：全局（添加、设置、排序）在侧栏；服务器（参与自动挂载、共享列表、服务器设置）在右列；共享（自动挂载开关、状态、展开后的位置/手动/管理）在共享行。
- 侧栏头部为“服务器”标题加两个 28 pt 系统 Liquid Glass 符号按钮（`.buttonStyle(.glass)`、圆形、大尺寸）。删除底部动作栏与窗口工具栏里的全局项；窄窗把同一组符号放在根层工具栏。搜索仍由系统 `.searchable` 提供，位于侧栏顶部。
- 服务器页直接展示身份、服务器自动挂载开关和每行共享的自动挂载开关；共享行不再放“在 Finder 中打开”。服务器设置改为工具栏尾端 `slider.horizontal.3` 符号加原生 sheet，并从 sheet 删除与页面重复的参与开关。
- 共享展开区固定为：挂载位置（含位置不一致说明与“使用此位置”）→ 手动操作（按状态一个主按钮 + 弹出）→ 分隔线 → 编辑/移除。展开区不重复开关和状态，编辑/移除与位置分开。
- 反馈归属：为 `ApplicationModel` 增加 `messageSurface`（window/sidebar/settings/menuBar）；视图只显示自己的 surface。删除排序、添加、移除、挂载、弹出、整轮、使用当前位置等成功提示，状态与对象变化即反馈；排序失败改侧栏 alert（`orderIssue`），设置消息只留设置窗口；菜单栏只显示菜单栏动作的结果。
- 发现并修复窄窗列表顶部空白：窗口从宽窗跨到窄窗时，AppKit 在已经位于工具栏下方的列表上再次叠加 52 pt 顶部内容 inset。以 `ScrollInsetNormalizer` 清除重复 inset，并只在窄窗根列表与窄窗服务器页启用；宽窗仍使用系统自动 inset，因此宽度切换与窄窗推送后都不再出现空白带。
- 已知限制：`ScrollInsetNormalizer` 依赖 AppKit 的 `NSScrollView.contentInsets` 行为，属于对当前 macOS 27 SDK 的针对性修正，后续 SDK 升级需重新验证；浅色、较大文字、VoiceOver 与九语原生审校仍未完成。
