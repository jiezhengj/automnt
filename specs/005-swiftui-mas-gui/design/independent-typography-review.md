# 行长与换行

**结论：NOT_PASS（设计层，存在阻塞）。**

## 阻塞（T-01）：详情页主操作行没有重排或溢出策略，德语估算已超过可用宽度

证据：`design/interaction-prototype.html` 健康态详情把四个动作渲染为单个横向容器 `<div class="actions">`（`display:flex; gap:9px; flex-wrap:wrap`），在默认窗口下渲染为一行（见 `light-healthy.png`、`narrow-detail.png`，两者都显示“在 Finder 中打开 | 编辑… | 弹出 | 移除共享文件夹…”同一行）。`design/NativeDesignPreview.swift` 同样把动作放在 `HStack` 内，**没有** `wrap` 能力（SwiftUI `HStack` 不换行，溢出会被压缩或截断）。`contracts/experience-design.md` 明文要求“布局原型注明各窗口尺寸、工具栏、状态文字、控件位置、空白与滚动策略”，并规定“窄窗口……不通过截掉关键按钮适配宽度”——原型与原生预览都没有注明该项策略。

实测（按 macOS 推按钮常见内边距估算整行宽度；可用宽度=默认 900pt 窗口下详情内容区 563pt）：

| 语言 | 四按钮整行估算 | 可用 563pt | 判定 |
| --- | --- | --- | --- |
| zh-Hans | 420 | 563 | 通过 |
| ko | 402 | 563 | 通过 |
| ja | 475 | 563 | 通过 |
| en | 488 | 563 | 通过 |
| fr | 565 | 563 | **超出** |
| de | 655 | 563 | **明显超出** |

在 `narrow-detail.png` 的 600pt 窗口下，中文行 420pt 仍勉强通过，但法语/德语超出的幅度更大；而 `HStack` 在 SwiftUI 中不会像 HTML 的 `flex-wrap` 那样自动折行，溢出后果是压缩或截断，与契约“不截掉关键按钮”直接冲突。

严重度：**阻塞**。这是九语必然触发的布局缺陷，且契约要求的设计交付物（布局/滚动策略标注）缺失。

建议：在 `contracts/experience-design.md` 明确详情页动作行的窄窗与长语言策略，并同步三份产物。可选做法：把“移除共享文件夹…”移入工具栏溢出菜单或详情属性区，主操作行只保留“在 Finder 中打开 / 弹出”并用 `ViewThatFits` 或系统菜单兜底；或明确“主操作行只放一至两个动作，其余进 toolbar 的 More 菜单”。无论选哪种，都必须在原型与 `NativeDesignPreview.swift` 中以实际宽度演示一次 `ViewThatFits`/菜单降级，而不是继续假定单行足够。

## 非阻塞（T-10）：长段落说明句无行数与滚动策略

证据：`design/localization.md` 与原型中的说明句在真实系统字体下的单行宽度远超容器：弹出说明 `重新登录或网络环境变化前，Automnt 不会自动挂载此共享。你也可以现在重新挂载。` 486pt；对应英文候选 781pt。容器为 460–563pt，因此这些句子必然折成 2–3 行（中文）到 2–4 行（英文），德语/法语按同等语义还会更长。契约只规定“失败信息可读、下一步明确”，未定义最大行数、是否允许 `lineLimit`、超长时是否滚动或折叠。`visual-system.md` 也没有行长（measure）规范。

严重度：非阻塞（不影响可用性判断，但影响“是否发生截断”的可验收性）。

建议：在视觉规范中给出说明文字的最大行长/最大行数与超长处理（如允许换行、禁止 `lineLimit(1)`、必要时就地展开），并在 T030 用真实译文测量最长字符串。

# 间距与对齐

**结论：PASS（设计层），附一处需统一的分歧。**

证据：`design/visual-system.md` 明确“背景、separator、材料、焦点、控件尺寸与禁用状态由系统组件管理”“间距依上下文采用默认正文或 .footnote/.caption 等系统语义样式，不固定一个灰色”，`NativeDesignPreview.swift` 实际采用 `Form`/`Section`/`.formStyle(.grouped)`、`LabeledContent`，对齐交给系统组件，符合契约。

需统一的分歧：`interaction-prototype.html` 的 `.toggle{display:flex;justify-content:space-between}` 把开关右对齐、`.row{justify-content:space-between}` 把值右对齐；而 `NativeDesignPreview.swift` 用系统 `Form`/`LabeledContent`（系统决定对齐）。契约以系统组件为准，故以原生预览为正；但原型作为维护者审阅入口会呈现不同的对齐观感，容易被误当产品规范。建议在评审记录中显式标注该差异属模拟层，不作为间距/对齐判据。

# 按钮与菜单宽度

**结论：NOT_PASS（设计层，存在阻塞，与 T-01 同源）。**

## 阻塞（T-01 的同一根因，此处按控件列出证据）

详情页按钮见上节实测表。补充菜单与设置侧实测：

菜单栏菜单在原型中固定宽 305pt、内边距 15pt、按钮横向内边距 11pt×2，可用文字宽度约 253pt。按真实系统字体测量：

| 菜单/设置标签（估算译文） | 实测宽度 | 预算 | 判定 |
| --- | --- | --- | --- |
| Afficher la barre des menus à l’ouverture de session（设置开关） | 314 | 420（Settings minWidth 460 去内边距） | 通过但仅余约 25% |
| Afficher Automnt dans la barre des menus（设置开关） | 255 | 420 | 通过 |
| Diesen gemeinsamen Ordner entfernen …（菜单候选） | 251 | 253（菜单） | **仅余 2pt** |
| Automatisches Bereitstellen ausschalten（菜单） | 245 | 253 | 仅余 8pt |
| Automnt in der Menüleiste anzeigen（设置） | 217 | 420 | 通过 |
| Automatische Wiederherstellung（设置） | 197 | 420 | 通过 |

契约未给菜单项或设置开关规定宽度上限、是否允许换行、是否需要缩短术语或使用 `Menu` 的自适应宽度。

严重度：**阻塞**（菜单候选德语项在实测下只剩 2pt 余量，属“按设计就会截断”的边界，且契约未给它任何降级策略；本地化后长度只会更不确定）。

建议：为菜单项设定明确的长度预算并给出超限处理（缩短为系统术语、改用更短的 macOS 标准动作名、或允许菜单自适应宽度而非硬编码 305pt）；`NativeDesignPreview.swift` 的 `MenuBarExtra` 内容不应依赖固定宽度。同时为 Settings 开关标签规定“允许两行、必要时整体增高”的明确规则，而不是留默认。

## 非阻塞（T-02）：Settings 开关标签无增长余量

法语登录菜单开关估算 314pt 落在 420pt 预算内，但已占 75%，且更长的 macOS 标准变体（如带 “de la session”）会突破。契约与 `localization.md` 都未给这类标签规定增长余量或换行策略。建议在 T030 用真实 String Catalog 复测，并在规范中写明“开关标签允许换行、不截断”的规则。

# 表单标签与辅助说明

**结论：NOT_PASS（设计层，存在阻塞，见 T-03；另有非阻塞层级建议）。**

证据（正面）：`NativeDesignPreview.swift` 把辅助说明作为独立的 `.foregroundStyle(.secondary)` `Text` 放在开关下方，符合契约“开关名、当前状态、结果说明分开表达”“辅助说明使用 secondary 等语义层级”；`design/localization.md` 也为每个开关名与后果说明给出成对候选，并明确“独立 secondary 说明，不能塞进动作括号”。这一层实现得比其他项好。

## 阻塞（T-03）：VoiceOver 朗读顺序与可访问名称未逐页标注，原生预览无可访问性 API

证据：`contracts/experience-design.md` 明文要求“键盘顺序、默认/取消动作、Esc、返回、保存快捷键与 VoiceOver 朗读在原型逐页注明”。实测 `interaction-prototype.html` 全文**没有任何** VoiceOver 朗读顺序或朗读名标注（对 “VoiceOver” 的检索为空）；可访问性相关属性只有 3 处 `aria-hidden`、10 处 `aria-label`、1 处 `aria-live`，且全部属于评审工具层（场景选择、开关、进度条、提示区），不是产品逐页朗读规范。`NativeDesignPreview.swift` 对 `accessibility` 相关 API 的检索为**0 处**（无 `accessibilityLabel`、无 `accessibilityElement`、无 `dynamicTypeSize`），仅有 3 处 `frame` 尺寸约束。`FR-010` 要求“键盘焦点……VoiceOver 纳入视觉与可访问性验收”，`SC-004` 要求“所有关键控件具备正确可理解的辅助功能标识”。

严重度：**阻塞**。契约把逐页 VoiceOver 朗读标注列为原型交付条件，产物中不存在，且原生预览也没有任何可访问性声明，无法据材料判断“可理解的朗读名称”是否存在设计。

建议：在原型中按页补充朗读顺序与朗读名清单（含名称、副标题、开关状态、按钮动作后果的朗读文案），并在 `NativeDesignPreview.swift` 中为主要控件加 `accessibilityLabel`/`accessibilityHint`（或明确说明由系统组件默认承担、哪些控件需要补）。同时明确“空状态与工具栏同时存在‘添加共享文件夹’按钮”时两者的朗读名如何区分（见 T-08）。

## 非阻塞（T-04）：原型把开关与说明压在同一行右对齐

`interaction-prototype.html` 的 `.toggle` 把标题、说明与开关放在同一横向行（说明与开关都在右/同行），在德语/法语长文本下会挤压成多行并破坏“开关名—结果说明”层级；`NativeDesignPreview.swift` 的纵向堆叠才是契约要求的形态。建议在评审记录中标注该差异属模拟层，并以原生预览为层级判据。

## 非阻塞（T-08）：同名按钮与重复标题

空状态 `ContentUnavailableView` 的 `Button("添加共享文件夹…")` 与工具栏 `Button("添加共享文件夹", systemImage: "plus")` 名称高度相似，VoiceOver 下同屏出现两个近义按钮。建议工具栏与空状态使用可区分的朗读名（例如工具栏“添加共享文件夹”，空状态“添加第一个共享文件夹”），并在 T-03 清单中体现。

# 窄窗导航布局

**结论：PASS（设计层），但受 T-01 拖累。**

证据：`contracts/experience-design.md` 规定“窄窗口可以按列表→详情导航，但必须保留返回和选中项，不通过截掉关键按钮适配宽度”；`data-model.md` 规定“窗口/导航偏好可私有保存”；`interaction-prototype.html` 实现 `body.narrow`（隐藏侧栏、显示 `.backnav` 返回）与 `listview` 类（返回列表并保留选中），`narrow-detail.png`（600×1704）实际显示返回入口与保留的选中项，行为与契约一致。`NativeDesignPreview.swift` 未写窄窗代码，但用 `NavigationSplitView` 由系统折叠为单栏，属系统行为而非缺口。

受 T-01 影响：窄窗下动作行仍是单行 `HStack`，中文可行（420pt），德语/法语按上表必然溢出。故窄窗导航本身通过，但窄窗内的动作行不通过。

建议：随 T-01 一并解决；在原型中保留“窄窗 + 完整九语字符串”组合的一页演示，而不是只用中文窄窗。

# 九语膨胀、截断、拥挤与布局跳动

**结论：NOT_PASS（设计层，未完成的发布缺口，且无膨胀预算）。**

证据：`design/localization.md` 明确“zh-Hant/ja/ko/de/fr/es/pt-BR 待本地化”“全部九语的……长文本/VoiceOver 验证未完成”“T060 不勾完成”；`tasks.md` 也把九语质量放在 T030/T036。设计材料中**没有任何按语言的长度预算或膨胀系数规定**（例如“德/法允许较中文增长 x%，控件不得截断”）。仓库内不存在任何本地化资源文件（`.xcstrings`/`.lproj` 全仓检索为 0），因此膨胀只能靠估算（本报告上表）。

关于截断与跳动：`design/visual-system.md` 明确“状态更新——默认立即更新，无自定义过渡；新结果替代旧结果，不重置焦点/滚动位置”，这对“布局跳动”给出了正确方向（用无过渡 + 不重置位置降低跳动感）。但没有规定“文案长度变化引起的行数变化是否允许引发高度变化”，也没有规定列表/详情在语言切换后是否保持滚动位置。

**中文静态图不能证明九语通过**：`light-healthy.png`、`dark-settings.png`、`narrow-detail.png` 等全部为简体中文渲染，`visual-board.png` 也是同一批中文网页截图；它们既非九语，也非原生，不能用于任何九语布局结论。主报告已判定九语 NOT_PASS，本补充确认其成因包含“无膨胀预算”与“无九语布局产物”两项设计缺口，而不只是“译文未做”。

严重度：**阻塞**（相对 FR-023/SC-011 的发布门槛；对设计层是明确缺口，材料未虚报）。

建议：把“各语言长度预算/膨胀容忍”写入 `visual-system.md`；在 T030 用真实译文生成最长达七语的布局快照（含窄窗与菜单/设置），并将 T-01/T-02/T-10 的修正项作为其通过条件。

# CJK 与英文混排

**结论：PASS（设计层）。**

证据：`design/localization.md` 规定“品牌 Automnt 保持不翻译；SMB 等协议名保持准确”，实测候选串在中文、日文、韩文中均把 `Automnt`/`SMB`/`Finder` 作为拉丁串嵌入并保留系统字距（例如“在 Finder 中打开”96.9pt、“메뉴 막대에 Automnt 표시”140.9pt、“メニューバーに Automnt を表示”183.1pt），未出现用全角字母替代或多余空格的问题；日文使用全角空格分隔拉丁词（“Finder で表示”）符合日文排版惯例。混合串宽度均在容器预算内（最大 183pt ≪ 253/420）。

未发现混排缺陷。唯一提醒：`design/localization.md` 已注明“英文正式行为措辞须与最终 API 对齐”，该措辞变化会改变拉丁串长度，需在 T030 复测。

# 变量与复数

**结论：NOT_PASS（设计层，覆盖不足）。**

证据：`design/localization.md` 通知条目给出 `{count} 个共享文件夹未能自动恢复。打开 Automnt 查看详情或重试。` 与英文 `{count} shared folders couldn't be restored automatically…`，并注明“按语言 plural 资源；1 的英文单数另写”。`contracts/core-and-channels.md` 规定“N 是核心核对后的失败数量”。实测该句中文 358.6pt、英文复数形式 503.9pt，在 460–563pt 容器内会折行，但可接受。

缺口：只定义了英文的单复数分叉；其余八语均无 plural 规则；更关键的是 **N 的边界未定义**——当 N 为 0 时（核心规则是“当轮结束仍有失败才发”，故 0 应不发送，但设计未写明该断言与界面文案）以及中文等语言的量词/复数形态处理（中文“1 个/2 个”单复数同形，但日、韩、德、法、西、葡各有规则）没有资源级说明。`tasks.md` T030 提到“复数/locale 格式/伪本地化”，但设计层没有给出可据以实现的规则表。

严重度：**阻塞**（对设计交付是明确缺口；`FR-023` 要求“复数、长文本与系统语言切换可用”）。

建议：在 `localization.md` 补一张复数规则表（每种语言：plural 类别、N=0 是否出现、量词），并明确“N=0 不投递且无文案”的边界；在 T030 用真实 String Catalog 验证。

# 系统较大文字

**结论：NOT_PASS（设计层，设计缺口与未来真机验收需分开）。**

证据：

- 设计缺口：`design/interaction-prototype.html` 在 `body` 与标题上使用固定 px 字号（实测 `font:14px`、`.main h1{font-size:22px}`，另有 `font-size:26px/23px/17px/12px/11px/45px` 的多处固定值），不响应系统的文字大小设置。该文件是模拟层（`visual-system.md` 已撤销候选 01 的网页固定字号作为产品规范），因此**这本身不是产品缺陷**；但其后果是**无法用这张原型判断任何大文字行为**，而材料中也没有替代证据。
- 替代证据缺失：`NativeDesignPreview.swift` 只用语义字体，理论上会随系统文字大小缩放，但实测该文件对 `dynamicTypeSize` 或任何相关 API 的检索为 0 处，也没有任何“文字放大后布局是否仍然成立”的约束或说明；`design/visual-system.md` 只在资产/审校段落提到“大文字”，把它列为 T030/T036 的通过条件（“长文本/大文字有可访问名称”），而没有给出设计结论。
- 契约要求：`spec.md` 边界情景明确把“大文字”与“窄窗口、深色、辅助功能”并列为必须保证“关键信息和操作可见”。

分类结论：**“未在设计中说明大文字下的布局容忍与滚动策略”是设计缺口（非阻塞，因为‘使用语义字体’已构成隐含策略）；“大文字下是否真的不遮挡/不截断”是未来真实窗口验收项，本轮未验证。**

建议：在 `visual-system.md` 明确大文字策略（语义字体的缩放、哪些区域允许增高/滚动、动作行如何在放大后降级），并把它并入 T-01/T-02 的修正；真机大文字与增加对比度走查归入 T036，本轮不判通过。

# VoiceOver 阅读顺序

**结论：NOT_PASS（设计层，见 T-03）。**

证据与判定同“表单标签与辅助说明”节 T-03：契约要求原型逐页注明朗读顺序，产物没有；原生预览无可访问性 API；中文静态截图不能证明朗读顺序。真机 VoiceOver 走查属未来验收（U-02）。

补充：`interaction-prototype.html` 的 `render()` 每次重绘都会整体替换 `main.innerHTML`，`ann()` 也会重写标注区；`design/visual-system.md` 要求“状态刷新不抢焦点、不重置滚动和草稿”，但原型未实现焦点保持，也无法验证动态内容的朗读宣告顺序（`aria-live` 仅用于评审工具的 toast）。这属于设计未定义，建议随 T-03 一并补“刷新后焦点位置与朗读宣告”的规则。

# 设计缺陷与未来真机验收的区分

**属设计缺陷（本轮可判定，应在实施前修正）**：T-01 动作行与菜单宽度无重排/预算策略；T-03 VoiceOver 朗读名与顺序未逐页标注；T-07 复数规则与其他八语覆盖缺失；九语无膨胀预算与布局产物；大文字布局容忍未说明。

**属未来真实窗口验收（本轮不得判通过，也不得判失败）**：真实 macOS 27 窗口在系统较大文字/增加对比度下的实际布局；真实 VoiceOver 朗读顺序与朗读名是否可理解；真实九语译文长度与最终截断情况；真实 Settings/菜单窗口的自适应宽度行为；减少动态效果下的布局跳动表现；原型 `innerHTML` 重绘在真实产品中是否引发焦点/朗读问题。

**明确不构成证据的材料**：全部中文网页静态图（`light-*.png`、`dark-*.png`、`narrow-detail.png`、`visual-board.png`）不能证明九语布局、原生外观或大文字行为；`NativeDesignPreview.swift` 通过 SDK 类型检查（需 `-parse-as-library`，实测不加该参数会报 `'main' attribute cannot be used in a module that contains top-level code`）不代表真实窗口布局通过；HTML 的 `flex-wrap` 与 `aria-*` 不代表 SwiftUI 的原生行为。
