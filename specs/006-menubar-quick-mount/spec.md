# 澄清记录

## Session 2026-11-20 — 入口形态、反馈与门禁

- **问：菜单栏里加一个新项，还是改造现有项？** → **答：把现有「立即检查 / Check Now」改名为「快捷挂载 / Quick Mount」。** 理由：该动作本来就是"按配置跑一轮挂载"而不是只读检查，两个做同一件事的菜单项会让人反复猜哪个才是对的；项目交互原则要求同一动作只出现一次。
- **问：点击后如何告诉用户结果？** → **答：失败才提示，成功不提示。** 与既有「成功不弹提示、状态变化即反馈」一致；全部成功时不出现任何新增文案。
- **问：什么条件下这一项可用？** → **答：跟随现有规则——自动挂载已启用、本应用的后台挂载服务就绪时可用。** 不满足时该项置灰，并在菜单中给出原因与下一步，而不是点了没反应或只弹一句失败。

# 用户场景与验收测试

## 用户故事 1 — 一次点击按已保存的配置把共享文件夹挂回来（Priority: P1）

维护者在外面（或刚唤醒、刚换网络），需要读写某个共享文件夹，发现卷宗没挂上。他打开菜单栏图标，点「快捷挂载」，程序按当前配置像开机时那样跑一轮：按服务器顺序、按每个共享的启用状态去挂载可达的共享，不需要他逐层进服务器子菜单点每个共享。

**优先理由**：这是本 Feature 的全部价值。逐共享挂载已经存在，但一次要挂三四个共享时要重复"进子菜单→点挂载"多轮，菜单栏本应是"一键把该有的都挂回来"的地方。

**独立验收**：用程序自身生成的真实配置（至少两个服务器、含一个跨服务器同路径的共享），手动弹出全部已挂载共享，确认 `mount` 输出为空；打开菜单栏菜单点「快捷挂载」；等待该动作结束；再次检查挂载结果与菜单内各共享状态。全程不手动挂载任何单个共享。

**验收场景**：

1. **给定** 两个服务器各有已配置共享、当前均未挂载、两台主机都可达、自动挂载已启用，**当** 维护者点击「快捷挂载」，**则** 每个启用的共享都按配置路径挂载成功，菜单内不再显示可挂载状态，且没有任何成功提示。
2. **给定** 上一轮刚跑完且全部健康，**当** 再次点击「快捷挂载」，**则** 不重复挂载、不产生新的系统提示，界面状态保持。
3. **给定** 某个共享已由另一台主机（兄弟主机承载同一共享）挂载在配置路径，**当** 点击「快捷挂载」，**则** 该项保持可用状态，不被视为失败、不被重复挂载。
4. **给定** 某个共享在本会话中被用户手动弹出，**当** 点击「快捷挂载」，**则** 该共享按既有轮次规则保持不挂载、不计入失败，也不解除该共享的会话抑制。
5. **给定** 某个服务器当前不可达，其余正常，**当** 点击「快捷挂载」，**则** 可达服务器的共享正常挂载；不可达服务器下的共享不计入失败（不属于"尝试后失败"）。

## 用户故事 2 — 失败时说清楚是哪几个、为什么（Priority: P2）

一轮跑完但部分共享仍然挂不上（认证失效、配置路径被别的卷占用、服务器拒绝该共享等）。维护者需要在菜单里直接看到"哪些没挂上、大概是哪类原因、下一步做什么"，而不是回到主窗口逐行找状态。

**优先理由**：菜单栏是这种"顺手点一下"的场景里唯一可见的界面；没有失败说明，用户只能猜是不是没生效，然后反复点击。

**独立验收**：构造至少两种不同原因的失败（例如一个共享的凭据失效、一个共享的配置路径被本机其他卷占用），确认该轮观测里这些项为失败状态且原因为对应类别；点击「快捷挂载」；检查菜单内是否出现**恰好一行**合并说明，名称与原因与该轮观测一致，全部成功时不出现该行。

**验收场景**：

1. **给定** 三个启用共享中两个会挂载失败、原因不同，**当** 点击「快捷挂载」并等该轮结束，**则** 菜单内出现一行说明，列出未挂载的两个共享名称与各自原因类别；已成功的那个不被提及，也不出现成功计数。
2. **给定** 全部共享成功，**当** 该轮结束，**则** 菜单内不出现任何新增说明行（失败说明区为空）。
3. **给定** 失败说明已显示，**当** 维护者随后成功挂载了其中一个共享（逐共享「挂载」），**则** 说明按最新状态更新，不再把已挂载项列为失败。
4. **给定** 名称很长或译文很长（德语、葡萄牙语），**当** 说明行显示，**则** 文本换行不截断关键信息，完整值可通过可访问名称读到。
5. **给定** 该动作未产生任何"尝试后失败"的项（例如全被会话抑制或服务器不可达），**当** 该轮结束，**则** 视为无失败，不出现说明行。

## 用户故事 3 — 不可用时能看懂为什么，而不是点了没反应（Priority: P2）

自动挂载关闭、后台服务待用户批准、尚无配置、或正有另一个挂载/弹出在进行时，「快捷挂载」不能执行。维护者需要一眼看出"现在为什么不能用、要去哪里开"。

**优先理由**：这一项在菜单里位置显眼，是用户最先点的地方；把不可用做成静默置灰会让用户以为程序坏了。

**独立验收**：逐一切换四种不可用条件（关闭自动挂载、撤销后台服务批准、删除全部配置改用空配置、开始一次逐共享挂载使程序处于忙碌），每次打开菜单确认该项置灰且菜单内有一行对应原因与下一步；恢复条件后确认该项重新可用。

**验收场景**：

1. **给定** 自动挂载已关闭，**当** 打开菜单栏菜单，**则** 「快捷挂载」置灰，并显示"需要先开启自动挂载"的理由与下一步。
2. **给定** 尚无任何已配置共享，**当** 打开菜单栏菜单，**则** 该项置灰并说明需要先添加共享文件夹。
3. **给定** 后台挂载服务待用户批准或未就绪，**当** 打开菜单栏菜单，**则** 该项置灰并指向设置里的修复入口。
4. **给定** 正在执行一次逐共享挂载或弹出，**当** 打开菜单栏菜单，**则** 该项置灰（不排队、不重复提交），该动作结束后恢复。
5. **给定** 上述任一不可用状态，**当** 维护者尝试点击，**则** 不产生任何挂载动作、不写入配置、不弹出错误对话框。

## 用户故事 4 — 窗口菜单与菜单栏是同一个动作、同一个名字（Priority: P3）

习惯用键盘的维护者在主窗口用 ⌘R，期望它与菜单栏那一项是同一件事，名字也一致。

**优先理由**：同一动作两个入口不同名会让用户以为它们行为不同；快捷键是既有的效率入口，不应因改名失效。

**独立验收**：在主窗口「服务器」菜单确认该项名称与菜单栏一致、⌘R 仍触发同一动作；对照两处触发后的挂载结果与失败说明完全一致。

**验收场景**：

1. **给定** 主窗口打开，**当** 查看「服务器」菜单，**则** 该项显示为新名称，快捷键仍为 ⌘R，且在两处触发得到同一结果。
2. **给定** 用 ⌘R 触发后有失败，**当** 查看结果，**则** 失败说明的内容与菜单栏触发时一致（同一实现、同一文案）。

## 边界情景

- **无配置**：不执行、不写配置；置灰并说明先添加共享文件夹。
- **自动挂载关闭**：不执行（与现状一致——完整轮次要求本应用的后台挂载处于活动状态）；不为"手动一键挂载全部"新开一条绕过自动挂载的路径。
- **后台服务待批准 / 过渡中 / 修复中**：置灰并给修复入口，不静默失败。
- **忙碌**：正在执行逐共享挂载、弹出或上一轮尚未结束时不接受第二次提交。
- **配置在点击后被改动**：沿用既有做法——按最新 revision 执行，不覆盖用户刚改的配置；冲突时以最新配置为准，不写回旧值。
- **上一轮未收尾（超时 / 信号不可用）**：给出一句可执行的下一步（修复后台挂载后重试），不反复重试直到成功。
- **会话抑制中的共享**：不因本动作解除抑制，也不计入失败（用户是主动弹出的）。
- **同一共享被兄弟主机条目承载**：视为可用，不重复挂载、不计失败。
- **配置路径被其他卷占用**：计为失败，原因归类为路径冲突。
- **菜单在点击后立即关闭**：失败摘要常驻到结果变化，下次打开菜单仍可见，并在主窗口消息区显示同一句；这属于原生菜单行为的限制，不为此另造弹窗或通知。
- **DNS / 主机名解析失败**：计为不可达（不属失败），沿用既有轮次判定。
- **多次连点**：忙碌期间置灰，不产生多轮并发。

# 需求

## 功能与品质要求

- **FR-001**：菜单栏菜单中原「立即检查 / Check Now」位置的动作改名为「快捷挂载 / Quick Mount」，触发行为不变（仍是按配置执行一轮完整挂载评估）；同一菜单中不得出现第二个做同一件事的项。
- **FR-002**：该动作按维护者已保存的配置执行一轮完整评估，规则与开机登录、网络变化触发的后台轮次完全一致（服务器顺序、每共享启用状态、会话抑制、兄弟主机承载、恢复判定）；不得为它另写一套挂载逻辑，也不得新增受管进程（Constitution 原则 II）。
- **FR-003**：该动作不写入配置文件、不改服务器顺序、不改任何共享的启用状态、不解除会话抑制。
- **FR-004**：结果反馈只有一条规则——**全部成功时零提示**；存在"已尝试但未挂载"的共享时显示一行合并说明。
- **FR-005**：失败判定只看该轮观测——仅当共享所在服务器可达、该共享已启用、本轮实际尝试过、且最终仍不可用，才计入失败。不可达、未评估、会话抑制、未启用、已由兄弟主机承载的共享一律不计入失败。
- **FR-006**：失败说明按原因归类（认证失败、配置路径被占用、服务器拒绝该共享、超时等），使用用户可理解的表述，不显示内部错误码或状态机词汇；同一原因的多个共享合并表述，名称过长可截断但须提供可访问的完整值。
- **FR-007**：失败说明的位置与既有消息机制一致（菜单栏菜单内的消息区、主窗口消息区按触发来源分别显示）；**不发系统通知**。理由见「已定事项」：既有通知文案只讲"自动恢复未完成"，用在用户主动触发的动作上会讲错故事；要发通知必须新增第二种通知类型并重做九语复数，属独立改动。
- **FR-008**：不可用时该项置灰，并显示与原因对应的一行说明与下一步（无配置 / 自动挂载未开启 / 后台服务待批准或未就绪 / 忙碌）。置灰项被点击时不得产生任何副作用，也不弹错误对话框。
- **FR-009**：执行期间沿用既有忙碌状态：不重复提交、不排队；结束后菜单与主窗口状态按该轮观测刷新。
- **FR-010**：主窗口「服务器」菜单中的同一动作同步改名，快捷键仍为 ⌘R，两处触发同一实现、同一文案。
- **FR-011**：所有新增文案（动作名、四种不可用原因、失败说明与其原因类别）在九种语言（en、zh-Hans、zh-Hant、ja、ko、de、fr、es、pt-BR）中提供，措辞沿用既有「挂载 / Mount」动词，面向结果而非实现（不出现"一轮"、"评估"、"后台轮次"、"观测"等内部说法）。
- **FR-012**：不改变 CLI 行为与文案（`automnt` 无参数执行一轮挂载、spec 004 锁定的「立即重新挂载」字面保持不变）；不改变配置格式、文件位置、权限与签名要求；不新增网络调用或后台常驻进程。
- **FR-013**：该动作仍受既有门禁约束：自动挂载关闭时不提供绕过路径；后台挂载未就绪时不执行，只说明如何修复。
- **FR-014**：菜单项具备正确的可访问名称与禁用原因，VoiceOver 可读、键盘可触发；置灰状态与原因在最新 macOS 的原生菜单行为下正确播报。

## 命名与文案决定

- 动作名统一为「快捷挂载 / Quick Mount」，两处入口一致。**英文确定用 "Quick Mount"**（2026-11-20 定）：它与既有「Mount」动词同源，不暗示范围；"Mount All" 会承诺"全部"，而本动作按规则会跳过本会话被弹出的共享，名字与实际不符。
- 与 `specs/005-swiftui-mas-gui/design/localization.md` 中「挂载动作不加『快捷』」的基线存在偏离：该基线针对的是逐共享的定向挂载动作，而本项是**按配置一次性挂载全部**的独立动作；维护者 2026-11-20 明确要求此名，故在本 Feature 内按新名执行，并在计划阶段同步修订该基线文档以免后续再被当作违规。
- 需与 `specs/005-swiftui-mas-gui/spec.md` 中的「快捷挂载」（那里指逐共享定向挂载，会解除该目标会话抑制）区分：本 Feature 的同名项是**全量按配置挂载**，不解除抑制。计划阶段须在 005 的 spec/文档中补一句消歧，避免两个"快捷挂载"互相指错。
- 改名后菜单栏不再提供"只读检查"入口：该动作原本就会真的挂载，名实本就不符；只读刷新仍由主窗口刷新与打开菜单时的状态读取提供。这是有意取舍，记录在此。

## 关键对象

不新增持久化数据。只读取并使用：已保存的活动配置（服务器顺序、共享列表、启用状态、凭据引用）、该轮的每共享观测（状态 + 问题类别）、会话抑制集合、兄弟主机承载关系、后台挂载服务状态。

# 成功标准

- **SC-001**：维护者从菜单栏挂回全部已配置共享的操作数从"每个共享 3 次（进子菜单、点挂载、回上一层）"降为 **2 次（打开菜单、点快捷挂载）**，且不需要知道哪个共享是哪个。
- **SC-002**：全部成功时新增可见文案为 **0 条**；存在失败时新增可见入口**恰好 2 个**（一行摘要 + 一个「查看未挂载的共享文件夹」明细入口），摘要里的数量与实际未挂载数量一致，明细逐项与之一一对应。
- **SC-003**：四类不可用条件（无配置、自动挂载关闭、后台未就绪、忙碌）下 **100%** 置灰且各有一行原因与下一步；置灰点击的副作用次数为 0。
- **SC-004**：九种语言的名称、四种不可用原因与失败说明全部有译文，`scripts/verify-localization.py` 通过，且新增 key 不出现在"非英文与英文逐字相同"清单里；不出现内部术语。（修订：原写 `--require-translated`。该模式忽略文档化的品牌/借用词 allowlist，而 `Automnt`、`Notifications`、`Port` 等既有 key 在九语中本就不翻译，基线状态下即不可能通过；项目实际门禁是默认模式 + allowlist。）
- **SC-005**：窗口 ⌘R 与菜单栏项触发同一实现（同一代码路径），两处结果一致；CLI 行为与文案零变化（既有测试与 `--self-test` 全通过）。
- **SC-006**：真实运行环境验证：在外网、卷宗全未挂载的状态下，一次点击把可达共享全部挂回（零提示）；失败场景下重新打开菜单即可看到正确的一行摘要与逐项原因，且无系统通知弹出。

# 假设与依赖

- 假设「快捷挂载」＝**改名 + 结果说明 + 可见的不可用原因**，不改变底层轮次语义；若维护者希望它在自动挂载关闭时也能执行，需要另行决定并可能触及 Constitution 原则 II（后台 owner），不在本 Feature 默认范围内。
- 依赖既有的完整轮次实现（`tryFullRound`）、每共享观测与可用性状态、本地化校验脚本与九语资源；不新增第三方依赖。
- 不依赖系统通知通道：反馈只走菜单与主窗口消息区，因此不涉及通知授权状态；未获通知授权的用户看到的结果与他人一致。
- 英文最终用词（Quick Mount / Mount All）与失败说明的合并句式在计划阶段定稿；两者都不改变本 spec 的行为要求。
- 本 Feature 不改 CLI、不改配置格式、不新增常驻进程、不做后台自动重试与进度条，也不调整菜单栏图标默认关闭的策略（spec 005 FR-019 不变）。

# 已定事项（2026-11-20 维护者授权由实现方定）

- **失败时是否发系统通知**：**不发**（修订自计划阶段的初稿）。既有通知通道的唯一文案是「Automnt：自动恢复未完成 / N 个共享文件夹未能自动挂载」，只服务于后台自动恢复失败；用户主动点「快捷挂载」却收到"自动恢复未完成"，等于讲错了故事。要发一条措辞正确、九语复数齐备的通知，需要新增第二种通知类型并同时改 Core、Platform、CLI 与两处本地化资源，与"在菜单里加一个动作"不成比例。改为：失败摘要常驻在菜单里直到结果变化，并提供可展开的逐项说明；主窗口消息区显示同一句。独立的通知类型记为后续可选项，不在本 Feature 内。
- **英文标签用词**：**Quick Mount**（理由见「命名与文案决定」）。
