# 核心原则

## I. 配置数据只能来自真实探测或使用者的明确输入

程序不得在源码、交互默认值或回退逻辑中写入特定用户环境的地址、主机名、共享路径或用户名。所有配置值只能来自运行期的真实探测或使用者的明确输入。开发与验证过程不得手工伪造业务配置：配置必须由程序自身的初始化与配置功能生成。凭据不得写入配置文件或日志。

## II. 不得引入第二个常驻运行进程

程序的后台评估必须由系统提供的服务机制按需启动，不得为实现同一目的再引入一个常驻等待进程，也不得让配置入口与后台服务各自维护独立的运行循环。

## III. 每个用户配置只有一个活动来源

后台服务与交互入口必须读取同一份活动配置；迁移不得造成多份可独立编辑的活动配置长期并存。迁移的具体交互方式由对应的 Feature 规格决定。

## IV. 版本与发布产物必须来自同一真理来源

程序版本只在一处维护。配置中的版本、命令输出、发布 Tag 与发布标题必须与该值一致；正式发布物必须与源码版本一致，不得出现二者脱节。

## V. 正式运行产物必须保持稳定签名与升级授权连续性

所有正式分发、自动更新及安装到用户正式运行路径的可执行产物，必须使用可被 macOS 验证的稳定代码签名身份。跨版本必须保持一致的代码签名标识与兼容的指定要求（Designated Requirement，即系统识别同一程序身份的签名规则），不得以未签名或临时签名产物替代正式运行产物。仅保持文件名或安装路径不构成稳定身份。稳定身份不限定为 Developer ID：免费 Apple 账号的固定 Apple Development 证书、Team ID 与代码标识可用于本机安装及跨构建身份验证，必须检查签名有效性与指定要求兼容性，不得把开发签名直接认定为满足其他设备分发、Gatekeeper 或公证条件。面向其他用户的发布须按实际分发渠道另行验证身份、系统接受性及授权连续性；本机验证结果不得外推为所有用户已通过。

用户完成首次必要授权后，正常版本升级不得仅因重新编译或替换二进制而要求用户再次允许网络卷访问或其他已经授予的同类权限。这是所有升级用户的产品体验约束，也是在无人值守场景下可靠运行的前提。首次安装授权、用户主动撤销授权、系统策略变化，以及新增权限或经维护者明确批准的身份迁移，必须与正常升级区分，不得用这些例外掩盖常规更新的重复授权。

发布与升级验收必须验证产物签名有效、跨版本身份要求兼容，并在已授权的真实 macOS 环境中完成升级前后权限连续性验证。仅构建成功、自测通过或单次运行无提示，不足以证明满足此原则；未验证或验证失败时不得宣称满足发布条件。证书续期或轮换必须保留授权连续性；如无法保留，必须先由维护者明确批准迁移方案及其用户影响。

不得通过修改 TCC 数据库、关闭系统隐私保护、自动点击授权弹窗或其他绕过系统授权的方式满足验收。签名凭据不得写入源码、业务配置或日志；签名身份与证书管理的具体实施方案由对应 Feature 设计与发布流程落实。

# 项目约束

## 凭据

SMB 凭据由系统钥匙串管理；程序不得把密码写入配置文件或日志。

# 治理

本 Constitution 只承载持久工程原则；产品决策由 Feature 规格承担，流程与发布规则由项目根 AGENTS.md 承担，避免宪法条款与产品决策的变更相互干扰。修改本文件时必须说明变更范围与理由，并按 SemVer 规则递增版本。产品、安全、隐私、数据保留与发布决定必须由维护者明确给出或标为待确认，不得用未声明的行业默认值替代。
