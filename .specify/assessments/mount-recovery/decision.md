## 根本问题的正面回答（v4 的立论基础）

**能识别。** 判别不依赖读取卸载意图（该路线已被 DA 头文件实锤死亡），而依赖三重信号，其中第一重已被本机 72 小时真实数据实测证实：

1. **结构性不对称**：网络丢失不产生卸载——smbfs 原地重连（12+ 次 `smb_iod_start_reconnect`，id 1→59），挂载全程在表；用户弹出才是真卸载（diskarbitrationd 通道）。故“缺失=曾被卸载”可靠。
2. **归属排除法**：automnt 的记录只有两本——挂载账与死卷清理账（**automnt 无弹出功能、永不提供**）；卷缺失且非清理账所致=用户弹出 → 抑制。无需记录/识别用户动作，排除法即归因。
3. **修复弹出判别**：卸载前的会话丢失日志证据区分“弹掉死卷”（修复→恢复）与健康弹出（意图→抑制）。

残余不确定度（健康弹出样本未捕获、系统强制卸载边界、日志 API 漂移）失败方向全部安全（保守抑制+一键兜底），对照实验列为验收校准项而非可行性门槛——故 go 的前提在裁决前已由实测支撑。

## Verdict & Rationale

**go。** 三轮质询分别修正了流程（调研先行）、覆盖面（台账降级为信号之一）、立论（先答“能不能”）。v4 的 go 立在实测证据上：丢失与弹出在系统层形态分明（72h 真实数据），归属可用排除法完成，修复弹出可用丢失证据日志判别；所有残余不确定度的失败方向均为“少恢复+可见兜底”，不触碰“误覆盖手动卸载=0”红线。

## If go — Handoff to `$speckit-specify`

- **Problem**: SMB 挂载因非用户意图丢失后无傻瓜化恢复路径（守护触发面缺口 + WatchPaths 官方竞态缺陷），非技术用户只能重启。
- **Chosen approach**: **B' 分层恢复 + 三重信号判别**：
  - L1 可达性迁移恢复（主症状）；L2 会话级抑制（已拍板语义）；L3 stale 清理+记账恢复（既有能力）；L4 通知/一键兜底；
  - 判别层：缺失且非清理账所致=用户弹出→抑制（automnt 无弹出功能）；在表失效=丢失→恢复；缺失+卸载前丢失证据=修复弹出→恢复；任一信号缺失→保守抑制。触发模型：纯事件唤醒（登录/网络变化/挂载命名空间变化），不轮询；C（周期兜底）为备选。
  - 备选 C（升级形态）保留。
- **In scope / out of scope**: 见 concept.md；配置数据模型零变更约束（抑制/台账状态持久化最小形态须过审查）。
- **Success metrics**: 非用户意图丢挂载无需重启恢复；**误覆盖=0**；会话内零打扰；死角有可见一键路径；宪法 II 合规。
- **Carried-forward（校准/审查，不阻塞立项）**:
  - 对照实验：真实 Finder 弹出 + 真实断网各一组日志/挂载表快照（触碰真实挂载，需维护者批准时机）——锁定健康弹出样本与系统强制卸载边界。
  - 内核日志信号的版本漂移对策（信号缺失→安全失败路径的测试）。
  - WatchPaths 漏事件风险的修复评估。
  - 宪法 II 合规审查、症状个案根因取证、问题规模数据。
